# P133 文件库明细页

## 本次调整
- 列表默认排序改为手动排序，持久化字段为 `STS_FILE.SORT_NUM`。
- 交互式网格新增 `排序` 列，支持在当前文件夹下拖拽调整顺序。
- 左侧文件结构树与右侧列表都按 `NVL(SORT_NUM, 999999), FILE_ID` 展示。
- `更新时间` 列继续复用 IG 原生排序能力，不额外定制排序切换逻辑。
- 文件夹行的 `更新时间 / 更新人` 改为递归统计该文件夹下所有子层级文件的最新 `UPDATE_DATE / UPDATED_BY`；文件行仍显示自身更新时间与更新人。

## 页面实现说明
- 页面：`P133`
- 主要区域：
  - 左侧树区域 `tree`
  - 右侧交互式网格区域 `content`
- 拖拽排序实现参考：`energy-storage@dev` 的 `P133`
  - 前端在 `content` IG 上做原生行拖拽
  - 后端通过 on-demand 进程 `SAVE_FILE_CHILD_ORDER` 保存排序

## 数据来源
- 列表主表：`STS_FILE`
- 文件夹最新更新时间聚合：
  - 从当前文件夹下一级文件夹开始 `START WITH`
  - 通过 `CONNECT BY PRIOR FILE_ID = PARENT_FOLDER_ID` 递归获取所有后代
  - 仅取 `FILE_TYPE = 'FILE'` 的记录参与聚合
- 更新人显示沿用页面已有 LOV 配置

## 注意事项
- 拖拽排序保存后会刷新右侧列表和左侧树。
- 若文件夹下暂无任何文件，则该文件夹的聚合更新时间与更新人可能为空。

## 2026-06-03 上传下拉与文件夹上传修复
- 上传按钮保持点击下拉模式，下拉项为文件上传和文件夹上传。
- 文件上传改为使用当前项目通用的 `s3Client.uploadFile(file, { isPrivate: true })` API，修复选择文件后没有进入上传流程的问题。
- 文件夹上传解析浏览器提供的 `webkitRelativePath`，先通过 `P133_CREATE_FOLDER_UPLOAD` 按层级创建或复用文件夹，再把文件上传到对应文件夹。
- `P133_SAVE_UPLOAD` 支持 `apex_application.g_x06` 作为目标父文件夹 ID，确保文件夹上传时文件记录落入正确目录。
- 上传完成后刷新右侧 `content` IG 和左侧 `tree` 区域。

## 2026-06-03 重命名后更新人显示修复
- P133 的重命名操作通过 P135 重命名弹窗完成。
- 文件夹行的 `更新人 / 更新时间` 优先显示文件夹自身的 `UPDATED_BY / UPDATE_DATE`，为空时再回退到递归子文件最新操作信息，最后回退到创建人/创建时间。
- P135 重命名文件夹并递归更新子级路径时，子级记录的 `UPDATED_BY` 改为当前登录用户 `:MPF_USER_ID`，避免写入 `-1` 后在 P133 用户 LOV 中显示为空。

## 2026-06-03 拖拽上传与中文提示修复
- 上传成功提示统一为 `上传完成`，上传失败提示统一以 `上传失败` 开头，避免页面展示英文错误提示。
- `upload_drop_zone` 拖拽区域新增 `dragenter`、`dragover`、`dragleave`、`drop` 事件处理，拖入文件后会进入现有上传队列。
- 拖拽文件夹时通过浏览器 `webkitGetAsEntry()` 递归读取目录树，保留相对路径，复用 `P133_CREATE_FOLDER_UPLOAD` 创建目录层级，再通过 `P133_SAVE_UPLOAD` 上传文件记录。
- 拖拽上传完成后刷新右侧 `content` IG 与左侧 `tree` 区域。

## 2026-06-03 上传保存返回 JSON 修复
- 修复上传后浏览器报 `Unexpected token 'O', "OK" is not valid JSON` 的问题。
- 根因是 `P133_SAVE_UPLOAD` 成功时返回纯文本 `OK`，但前端 Ajax 链路按 JSON 解析响应。
- `P133_SAVE_UPLOAD` 现在成功返回 `{"status":"success","fileId":...}`，异常返回 `{"status":"error","message":...}`。
- 前端保存上传记录时显式使用 `dataType: 'json'`，并校验 `data.status === 'success'` 后才继续上传队列。

## 2026-06-03 中文文件名与默认同步状态修复
- P133 上传文件与上传文件夹时，文件名/文件夹名参数改为原样传值，不再前端手工 `encodeURIComponent`；由 APEX 请求传输层负责编码，后端继续使用单次 `UTL_URL.UNESCAPE` 兼容解码，避免中文名称落库成 `%E4%B8%AD...`。
- `STS_FILE.NEED_SYNC` 默认值调整为 `0`，与 P133 页面 `未同步=0 / 已同步=1` 的状态映射保持一致。
- 因默认值改为 `0`，后续新增文件记录默认显示为 `未同步`，只有执行同步动作后才变为 `已同步`。

## 2026-06-04 上传 ROOT_FOLDER_ID 修复
- `P133_CREATE_FOLDER_UPLOAD` 与 `P133_SAVE_UPLOAD` 不再只依赖 `FILE_LEVEL=1` 分支判断根目录。
- 两条上传链路都会先读取父记录的 `ROOT_FOLDER_ID`，优先继承真实根目录。
- 若父记录根目录为空，则回退到页面当前根目录 `P133_ROOT_FOLDER_ID`；再为空时回退到当前父目录 `FILE_ID`，避免新增目录或文件出现 `ROOT_FOLDER_ID` 为空。
- 已在 `sales-tools@test/f138` 导入 `P133` 并执行真实文件夹上传验证，新建目录和目录内文件的 `ROOT_FOLDER_ID` 均正确写入根库 `40021`。

## 2026-06-05 文件夹批量上传失败回退修复
- 文件上传、文件夹上传、拖拽文件夹上传统一走 `runUploadBatch(...)`，同批次内任一文件保存失败即中止后续上传。
- 前端会记录本次批量上传新建的目录和文件 `FILE_ID`，失败后调用 `P133_ROLLBACK_UPLOAD_BATCH` 统一回退，避免页面残留半成品目录。
- `P133_CREATE_FOLDER_UPLOAD` 新增 `created` 标记，仅回退本次新建目录，不误删原本已存在的目录。
- 已在 `sales-tools@test/f138` 导入 `P133` 并通过浏览器模拟第二个文件保存失败验证：失败后页面不保留本次目录，数据库内已创建记录被软删回收。
